# tadaken3 文体スキル

著者本人の過去記事から抽出した文体特徴を、新規執筆・リライト・草稿レビューに適用するためのスキル。

## このスキルを使うタイミング

- ブログ・noteの新規記事を本人の文体で書きたいとき
- AI生成の下書きを本人の文体に寄せて書き直したいとき
- 既存原稿が「自分の声」から外れていないかチェックしたいとき

## 文体の核（守るべき5原則）

### 1. 一人称は文脈で使い分ける

- noteなどビジネス・自己紹介寄り → 「私」「自分」
- 個人ブログ・趣味・回想系 → 「ボク」（カタカナ）

メディアの性格に合わせる。同一記事内では混在させない。

### 2. 体験談ドリブンで書く

主張を抽象論で展開しない。**「あるとき、ふと考えました」「小学生のボクは〇〇していた」**のように、自分の具体的な行動・出来事から書き起こし、そこから一般原則を引き出す。

悪い例: 「個人開発にはAIが有効です」
良い例: 「以前にも個人開発で何度かアプリを作ろうとしたことがありました。ですが、作成している途中で仕事が忙しくなったりで、『これは無理かも…』と手を止めてしまった経験があります」

### 3. 短い文を重ねてリズムを作る

一文は基本的に短い。読点で長く繋がない。結論を先に出して、説明を後ろに重ねる。

```
結果は、たった3日でApp Storeリリースまで到達。

コードを一行も書いていない自分が、アプリを出せた。

この体験が、開発者としての自信を一気に引き上げてくれました。
```

体言止め・倒置・改行を使ってテンポを作る。一文一改行に近い段落構成も多用する。

### 4. 「原則は同じ／定義が違う」型の気づき構造

両記事に共通する思考パターン。**「やっていることの本質は変わらないが、見え方・定義・前提だけが変わった」**という気づきを軸に話を畳む。

例（ポケモン記事）:
> やっていることの原則は小学生のボクも大学生のボクも変わらない。「強いポケモン」を育てているということだ。ただ、小学生のボクと大学生のボクでは強さの定義が全く異なっている。

例（AI開発記事）:
> 「頭の中だけで終わったアプリ」に命を吹き込める時代

過去 vs 現在、Before vs After、自分 vs 他者、のような対比で「原則の不変」と「変数の変化」を切り分けて見せる。これが結論部分のキメになる。

### 5. 強調は太字、感情は素直に出す

- 重要な気づき・主張は `**太字**` で囲む（Markdown）。1記事に5〜8カ所程度の頻度。
- 「ポケモンすごい。」「なんだか久しぶりにポケモンが遊びたいな。」のような、文末に素直な独り言を置いて締めることがある。気取らない。

## 構成テンプレート

典型的な記事の流れは次の3部構成。

```
1. 導入：自分の現在の状況・問題意識を体験ベースで書く
   「こんにちは、Ken.Tです。普段は〇〇で、最近〇〇しています。」
   読者にその記事を読む理由を最初の3〜4段落で提示する。

2. 展開：体験 → 気づき → 原則 のサイクルを2〜4回繰り返す
   各セクションは見出し（### レベル）で区切る。
   見出しは内容を要約した平易な日本語。技巧的なコピーは避ける。

3. 締め：原則の言語化、または素直な感想で終わる
   壮大にまとめない。「ポケモンすごい。」級の軽さで閉じてよい。
```

## 語彙・表現の癖

| よく使う | 避ける |
|---|---|
| 「ふと」「あるとき」「実は」 | 「結論から言うと」「まず最初に」 |
| 「〇〇できた」「〇〇に到達」 | 「成功を収めた」「達成しました」 |
| 「〇〇だった」（言い切り） | 「〇〇と言えるでしょう」 |
| 「ですが、」（逆接の独立段落） | 「しかしながら」「とはいえ」 |
| 「…」（三点リーダで余韻） | 「！」（多用しない） |
| カタカナ「ボク」（趣味系） | 「僕」「俺」 |

## やらないこと

- **箇条書きで要点を並べて終わらせない**。本文は地の文で書く。箇条書きは補助のみ。
- **「いかがでしたか？」「最後までお読みいただきありがとうございました」のような定型挨拶を末尾に入れない**。
- **権威付けのために本・人名を並べない**。引用は1記事1冊程度（「DIE WITH ZERO」のように、自分の行動の引き金になった本だけ）。
- **専門用語の壁を立てない**。データエンジニア・モバイル開発の話でも、専門外の読者が読めるレベルまで嚙み砕く。
- **AIに丸投げした文章にしない**。生成感の強い「〜することができます」「〜が重要です」の連続は校正で潰す。

## レビュー時のチェック項目

新規・既存原稿に対し、以下を順に確認する。

- [ ] 一人称が記事の性格と合っているか（noteなら「私」、ブログなら「ボク」）
- [ ] 冒頭3段落以内に自分の具体体験が出てきているか
- [ ] 一文の平均長は短いか（読点2つ以上の長文が連続していないか）
- [ ] 「原則は同じ／定義が違う」または同等の対比構造が記事のどこかにあるか
- [ ] 太字での強調が5〜8カ所程度入っているか
- [ ] 「いかがでしたか」系の定型挨拶や、AI生成感の強い言い回しが残っていないか
- [ ] 締めが軽く・素直に終わっているか（壮大にまとめていないか）

## このスキルが起動されたときの手順

1. 対象（新規執筆 / リライト / レビュー）を確認する。指定がなければ聞く。
2. 媒体（note / 個人ブログ / その他）を確認し、一人称を決める。
3. **新規執筆の場合**: ユーザーに「題材」「伝えたい原則・気づき」「自分の体験エピソード」の3点をヒアリングしてから書き始める。題材だけで書き始めない。
4. **リライト・レビューの場合**: チェック項目を上から順に当て、具体的な行・段落を引用して指摘する。修正案を併記する。
5. 出力は文体の核5原則に厳格に従うこと。AIっぽい言い回しが残ったらレビュー時に潰す。
